# 全界面操作与自动化方案

日期：2026-09-08（含多角色评审后的修订）
目标：
1. 整个产品流程在 UI 中完成，日常使用不需要命令行；
2. 系统默认全自动推进，人只在选择干预时介入。

本文只讨论如何达成这两点，不重述已实现的能力。涉及的表名、路由、文件均为当前仓库中的真实位置。

> **实现状态（2026-09-08）**：P0–P2 的仓库实现已落地，P3 已完成应用侧身份接入能力但仍依赖仓库外认证代理与真实账号验收。实现映射见
> [docs/IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md) 的 UI-P0 / UI-P1a / UI-P1b / UI-P2 / UI-P3 行。
> **自动建项目默认关闭**（§2.3 的证据区分度指标当前不达标）。生产身份、真实 G7 双账号、真实供应商与无人值守观察期均不能用本地测试代替，当前不标记为 Accepted。

---

## 1. 现状与差距

### 1.1 初始差距与当前修复

`/projects/{id}` 工作台已经能调用：研究与证据编辑、脚本/分镜保存、四类审批、状态转换、
配音与渲染入队、资产上传、发布包生成、YouTube 上传、指标快照。选题页能导入文章、核验选题、创建项目。

多角色审查识别出的三项运行缺口已经在仓库中补齐；是否可用仍取决于目标环境是否实际启动服务并配置凭据：

| 初始缺口 | 当前仓库实现 |
| --- | --- |
| Render Worker 需人工启动 | compose 常驻服务、独立 15 秒注册心跳、60 秒孤儿作业告警与 15 秒界面轮询 |
| 无常驻调度器 | 独立 `scheduler` 服务调用有界编排引擎；手动 HTTP 路由只跑一轮 |
| 健康状态只能靠脚本 | `/settings/diagnostics` 显示数据库、迁移、存储、凭据形状、Worker、积压与最近 tick |

### 1.2 流程本身没有自动推进

每一步状态转换都要人点。即使门禁全部通过、没有任何需要人判断的内容，
项目也不会自己往前走。当前不存在编排器，也不存在「自动化策略」的概念。

## 2. 三个必须先讲清的前提

### 2.1 机械步骤与问责步骤要分开

这个系统的产品前提是**证据优先、人对内容负责**。G3（研究）、G4（脚本）、G6（人工终审）、
G7（独立发布批准）四道门禁存在的意义就是「必须有具体的人对这条内容签字」。

**把这四道门禁改成无条件自动通过，等于删掉这个产品的核心属性**，
对受监管题材还有实际的合规与声誉风险。

因此区分两类步骤：

- **机械步骤**——采集、聚类、建项目、配音、渲染、自动 QC、发布执行、指标回流。
  没有判断成分，**默认全自动**。
- **问责步骤**——上述四道审批。**默认仍需人确认**，但提供一条
  **可撤销、有范围、留痕的预先授权**通道（详见 §5.2）。

### 2.2 自动化不能凌驾于职责分离之上

G7 的判定是 `publishApproval.actor_id !== researchApproval.actor_id`。
如果同一个授权人同时自动放行研究与发布，这条约束就形同虚设。

**硬性规则**：研究类自动授权人与发布类自动授权人必须是**不同的真实成员**，
在策略保存时校验、在自动放行时再校验一次。默认配置下发布审批**不参与**自动放行。

### 2.3 选题质量是自动化的前置条件，目前不达标

实测发现：当前聚类在英文来源上失效——100 篇文章被并成一个话题，
三条声明的「证据」指向同一批文章、没有区分度。`lib/domain.ts` 的分词与主题词表
是按中文语料调的。

**在选题质量可度量并达标之前，自动建项目必须默认关闭**，否则自动化只会批量生产语义混乱的内容。
需要先落地的度量（写入 `topics.quality_json`）：

- 簇内主题一致性（文章间关键词重合度分布，而不是只看来源数）；
- 声明与证据的对应关系是否唯一（同一条证据不应同时支撑多条互不相关的声明）；
- 语言与词表匹配度（当前词表只覆盖中文语料时，英文簇直接标记为不可自动化）。

不达标的选题只进待办箱，不自动建项目。

## 3. P0：把界面补成完整闭环

目标：任何日常操作都能在界面完成，命令行只保留部署与排障。

### 3.1 Worker 不再由人启动

- Worker 作为常驻服务部署（`docker compose` 增加 `render-worker` 服务，
  复用 `render-worker/Dockerfile`），随控制面一起起停，配 `restart: unless-stopped`
  与内存上限（Chromium 较重）。
- 新增 `workers` 表：`id`、`hostname`、`kinds`、`last_heartbeat_at`、`version`。
  Worker 空闲轮询时也上报心跳（`POST /api/v1/workers/heartbeat`）。
  **超过 7 天未心跳的行由调度器清理**，避免无限增长。
- `/operations` 展示在线 Worker 数、各类型作业积压、最近失败。

### 3.2 界面提示「作业不会被执行」

工作台入队后，如果 60 秒内没有任何在线 Worker 能处理该类型作业，
在项目页顶部显示明确告警并给出原因。

### 3.3 系统自检面板

新增 `/settings/diagnostics`，把 `scripts/check-storage.ts` 的判定逻辑做成
`GET /api/v1/diagnostics`，返回：数据库连通、迁移版本、对象存储读写、
OpenAI 凭据、YouTube 凭据、Worker 在线数、队列积压、**调度器上次 tick 距今时长**。
凭据类只报「可用/不可用/未配置」和具体原因，不回显任何密钥。

### 3.4 脚本长度前置校验

当前脚本长度与目标时长不匹配时，要到 G5 或自动 QC 才失败，反馈链太长。

- `lib/script-duration.ts`：按语言给出朗读速率（中文实测约 3.86 字/秒，英文按词计），
  估算旁白时长；
- 脚本编辑器实时显示「预计旁白 X 秒 / 目标 Y 秒」，超出 60%–110% 区间时标红说明原因；
- 自动生成脚本时按目标时长反推字数，而不是简单拼接标题。

**不允许为了迁就短旁白去缩短 `render.durationSeconds`**——那是发布阻断项，不是可调参数。

### 3.5 命令行脚本的归属

`scripts/walk-workflow.ts`、`scripts/ingest-real-feeds.ts` 是排障与冒烟工具，
不进入产品流程，README 中标注为开发者工具。
`db:migrate`、`drill:restore`、备份恢复保留在部署与运维流程里。

## 4. P1：自动推进引擎

### 4.1 调度器是独立进程，不是进程内定时器

vinext 没有 instrumentation / startup 钩子（其导出只有 `prod-server`、`fetch-handler`、
`app-router-entry` 等）。模块级 `setInterval` 只在该模块被首个请求引入时才启动，
dev 模式 HMR 还可能重复注册。

**因此调度器与 Render Worker 同构，是独立进程**：

- `lib/orchestrator.ts`：编排逻辑本体，纯函数式接口，接受 `now` 参数（与 `lib/` 现有约定一致，便于测试）；
- `scripts/scheduler.ts`：常驻进程，默认 30 秒一轮，调用 `lib/orchestrator.ts`；
- `docker compose` 增加 `scheduler` 服务；
- `POST /api/v1/scheduler/run` 保留为**手动触发的薄封装**，同样调用 `lib/orchestrator.ts`，
  但只处理一轮有限工作量，不承担无界编排（否则必然 HTTP 超时）。

### 4.2 并发与锁

- 每轮 tick 用 `pg_try_advisory_lock` 抢一个**短锁**，只用于选取本轮要处理的项目集合，
  选完即释放，不整轮持锁占用连接；
- 逐个项目处理时用 `SELECT ... FOR UPDATE SKIP LOCKED`，与作业租约机制保持一致；
- **每轮工作量有上限**（项目数、入队作业数、API 调用数），超出留到下一轮，
  避免积压导致 tick 相互重叠。

### 4.3 一轮 tick 做的事

按顺序，每步都受策略与配额约束：

1. **采集**：按 `schedule_cron` 找出到期且 `rights_status='approved'` 的来源，入队采集作业；
2. **选题质量评估**：计算 §2.3 的质量指标并写入；不达标的只进待办箱；
3. **建项目**：对达标且门禁通过的选题按策略创建项目；
4. **推进**：重算门禁，执行所有「门禁已过且在自动范围内」的转换；
5. **作业编排**：在正确状态下入队配音（`SCRIPT_APPROVED`）与渲染（`ASSETS_READY`）；
6. **发布**：G7 通过后按策略创建发布任务并推进到 `PUBLISH_SCHEDULED`；
7. **指标回流**：到达采集窗口（2h/24h/7d）时拉取或提醒录入；
8. **清理**：过期原文清理、过期 Worker 心跳清理。

### 4.4 引擎必须遵守的约束

- **只走状态机**：调用与界面相同的 `transitionContentProject`，不绕门禁、不直接写 `state`；
- **幂等**：每步用确定性幂等键，tick 重入不会重复入队；
- **预算与并发**：沿用 `MONTHLY_RENDER_BUDGET_MICROS` 与 `RENDER_CONCURRENCY_LIMIT`，
  并**按策略归集成本**，便于定位是哪条策略在烧钱；
- **失败不重试到死**：确定性失败（如自动 QC 未通过）直接终态失败进 DLQ——这已是现有行为，不得放宽；
- **熔断**：同一阶段连续失败 N 次（如对象存储或 OpenAI 不可用）即暂停该阶段并进待办箱，
  不在每轮 tick 里空转重试；
- **审计**：见 §5.4 的身份规则。

### 4.5 顺序陷阱由引擎消化

现存三个必须人肉记住的顺序约束，引擎接管后不再暴露给用户：

| 作业 | 必须在此状态入队 |
| --- | --- |
| 配音 | `SCRIPT_APPROVED` |
| 渲染 | `ASSETS_READY` |
| 发布任务 | 项目已在 `PUBLISH_SCHEDULED` |

另外 `RENDER_QUEUED` 目前没有回到 `ASSETS_READY` 的转换路径，误入后只能靠取消渲染作业
回到 `CHANGES_REQUESTED`。引擎不会制造这种状态，但**应当补一条
`RENDER_QUEUED → CHANGES_REQUESTED` 的人工回退**，避免误操作后无路可走。

## 5. P2：自动化策略与人工干预

### 5.1 策略模型

新增 `automation_policies` 表：

| 字段 | 说明 |
| --- | --- |
| `id` / `name` | 策略标识 |
| `scope_json` | 生效范围：品牌、语言、来源类型、选题分数与质量分下限 |
| `stages_json` | 每个阶段的模式：`auto` / `manual` / `off` |
| `auto_approvals_json` | 哪几道审批可自动放行及各自条件 |
| `research_authorized_by` | 研究/脚本类自动放行所依据的成员 |
| `publish_authorized_by` | 发布类自动放行所依据的成员，**必须不同于上一字段** |
| `guardrails_json` | 每日上限、静默时段、单条成本上限、最低独立来源数 |
| `authorized_at` / `expires_at` | 预先授权的有效期，过期即失效并转人工 |
| `enabled` | 总开关 |

默认策略：机械步骤 `auto`，四道审批 `manual`，自动建项目 `off`（待 §2.3 质量指标落地后再开）。

### 5.2 自动审批的条件（可配置，默认关闭）

举例——全部满足才自动放行，任一不满足即转人工：

- **G3 研究**：独立来源数 ≥ N，无未解决的反驳证据，选题质量分达标；
- **G4 脚本**：声明全覆盖，无违禁表述，预计旁白时长在区间内；
- **G6 终审**：自动 QC 24 项全过；
- **G7 发布**：默认**不自动放行**。若显式开启，必须满足以上全部条件，
  且当日自动发布量未超上限，且不在静默时段，且 `publish_authorized_by`
  与 `research_authorized_by` 为不同真实成员。

### 5.3 人工干预模型

- **随时接管**：项目页与自动化控制台都有「暂停自动化」，可按项目或全局暂停；
- **人一改，自动就停**：任何人对项目做了编辑或审批，该项目自动转人工，
  需要显式「恢复自动」才继续；
- **内容事件互斥**：项目一旦开了 `content_incidents`（勘误、下架、投诉），
  **立即退出自动化并禁止自动推进**，直到事件关闭。不能一边处理事故一边继续往发布推；
- **待办箱** `/inbox`：门禁未过、自动 QC 失败（附失败检查项）、DLQ 作业、
  证据冲突、超预算、熔断触发、策略拒绝的自动放行、质量不达标的选题；
- **触达路径**：全自动意味着人不盯屏幕，待办产生需要外部通知
  （Webhook 复用现有 HMAC 机制，或邮件），不能只躺在页面里；
- **自动化控制台** `/automation`：策略编辑、开关、近期自动动作时间线、自动/人工比例、
  当前熔断状态；项目页需显示**为什么暂停了自动化**，而不只是一个状态位。

### 5.4 自动动作的身份与审计

自动化不能凭空构造身份——`recordApproval` 会校验 `actor.role`
（`lib/control-plane.ts` 中 `roles[kind].includes(actor.role)`），
`transitionContentProject` 会校验 `transitionRoles`。规则：

- **机械步骤**：以注册在 `team_members` 中的服务账号身份执行，
  审计 metadata 记录 `trigger: 'automation'` 与 `policyId`；
- **自动审批**：以策略中对应授权人的**真实成员身份**写入 `approvals.actor_id`，
  note 中写明「依据策略 X 自动放行」。问责链因此指向具体的人，
  G7 的职责分离也据此成立；
- 审计读取方必须能一眼区分「人做的」与「策略做的」。

### 5.5 不做的事

- 不自动改写已批准的脚本内容；
- 不自动放宽任何门禁阈值；
- 不自动把 `SIGNAL40_ALLOW_PUBLIC_PUBLISH` 置为 true——公开发布始终是人的显式决定；
- 自动化失败不静默重试到成功，超过阈值一律进待办箱。

## 6. P3：生产身份（应用侧已实现，环境验收阻塞）

生产请求统一经 `resolveRequestActor` 解析可配置的受信身份头，并到 `team_members` 校验 active 成员；
界面通过 `/api/v1/session` 显示服务端认定的真实身份。`SIGNAL40_ALLOW_LOCAL_ROLE_HEADERS=false`
会关闭 localhost 开发身份模拟，选题相关路由也不再绕过统一策略。

仓库不包含认证反向代理或 OIDC 身份源，因此目标环境仍必须完成：代理注入头、未认证/离职/降权访问回归，
以及两个不同真实账号分别完成研究批准和 G7 发布批准。完成这些之前 P3 只能称为“应用侧已准备”，不能称为 Accepted。

## 8. 分期与验收

| 阶段 | 内容 | 验收标准 |
| --- | --- | --- |
| P0 | Worker 常驻、诊断面板、无 Worker 告警、脚本时长前置校验 | 从建项目到发布全程不碰命令行；配错凭据能在界面看到原因 |
| P1a | 选题质量指标 | 英文簇能被正确判定为不可自动化；指标可在界面查看 |
| P1b | 调度器进程与编排引擎 | 登记授权来源后，无人干预即可产出待审批成片；所有自动动作可在审计中追溯 |
| P2 | 策略、待办箱、控制台、通知 | 可按阶段开关自动化；人工编辑或内容事件自动暂停；被拒的自动放行进待办并触达 |
| P3 | 生产身份 | 非本地请求可正常鉴权；G7 的两个批准人是不同的真实账号 |

上述表格是验收标准，不是当前通过声明。仓库自动化可验证 P0–P2 的实现路径；P0/P1b 的真实常驻服务观察、P3 认证与真实账号仍需在 staging/production 产生独立证据。

每阶段回归口径不变：`npm run lint`、全量测试、100 场景门禁回归、迁移幂等、
恢复演练、构建、渲染冒烟全绿。

**编排引擎新增测试要求**（`lib/orchestrator.ts` 接受注入的 `now`，沿用 `lib/` 现有约定）：

- 门禁未过时不推进；
- tick 重入不重复入队；
- 策略过期后转人工；
- 自动放行下 `research`/`publish` 授权人相同时被拒绝；
- 预算耗尽、熔断触发后停止该阶段；
- 内容事件开启后自动化立即停止。
- 全局暂停后所有阶段均跳过；
- 单轮作业/发布/API 上限生效；
- 2h 快照不会屏蔽 24h/7d 提醒；
- 策略过期会禁用策略并把关联项目明确转人工。

## 9. 与现有约定的关系

- 门禁仍是契约，引擎只是替人点按钮，不改变判定；
