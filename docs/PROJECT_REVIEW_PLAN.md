# Signal 40 项目专业 Review 方案

> 文档状态：Re-review completed（本地整改已完成，目标环境验收待执行）
> 制定日期：2026-09-10
> Review 类型：发布就绪性技术审查
> 适用范围：控制面、API、来源 Worker、渲染 Worker、调度器、数据库、对象存储、视频生产链路与运维交付

## 1. Review 目标

本次 Review 不以代码风格检查为主，而是验证 Signal 40 在真实生产条件下是否满足以下目标：

1. G0–G8、证据绑定、异人审批等核心业务门禁不存在可绕过路径。
2. 身份、权限、来源授权、Secret 和 Worker 权限边界满足 fail-closed 原则。
3. PostgreSQL 事务、幂等、租约、分页提交、删除和恢复流程能够在并发及故障条件下保持一致。
4. OpenAPI、服务端实现、客户端调用和对外错误模型保持一致。
5. R2、OpenAI、YouTube、OpenCLI、真实来源和认证代理等外部依赖有明确的验证边界。
6. 所有主要页面具有统一的内容宽度、导航结构、响应式行为和可访问性基线。
7. 测试、CI、镜像、安全扫描、备份恢复、监控和回滚能力足以支持目标环境发布。

Review 结论必须区分 `Implemented locally → Delivered → Deployed → Integrated → Accepted`。不得仅凭代码存在、本地测试或模拟环境结果，将能力提升为 `Integrated` 或 `Accepted`。

## 2. 当前项目基线

基于 2026-09-10 的仓库检查：

- 技术栈：TypeScript、React 19、vinext/Vite、PostgreSQL、Drizzle、Cloudflare R2、Remotion、Docker。
- 主要规模：93 个 API 路由、68 个 `lib` TypeScript 模块、55 张表、33 个迁移、58 个测试文件。
- `npm run lint`：通过。
- `npm exec tsc -- --noEmit`：通过。
- `npm test`：268 项中 265 项通过；3 项真实 R2 契约测试因当前执行环境无法解析 Cloudflare R2 域名而失败。该结果应在具备网络权限且配置测试桶的 CI 环境复核，当前不直接判定为业务代码缺陷。
- 基线冻结时没有业务代码修改；工作区新增内容为本 Review 计划与 Review 产物。
- 已具备 OpenAPI 破坏性变更检查、迁移 checksum、镜像扫描、SBOM、恢复演练和渲染冒烟测试。
- 当前 CI 工作流未显式执行 `tsc --noEmit`，Review 中需要确认生产构建是否提供等价类型检查；若不能证明，应将独立 typecheck 加入 CI 门禁。
- 当前没有可见的测试覆盖率门禁；需要以关键路径追踪和风险场景覆盖为主，覆盖率数字作为辅助证据。

## 3. Review 原则

### 3.1 风险优先

关键写路径、权限决策、状态转换、外部发布、来源授权、删除及恢复路径必须 100% 审查；普通只读页面、展示组件和低风险工具采用抽样审查。

### 3.2 证据驱动

每项结论应至少绑定以下一种证据：

- 文件与行号；
- 自动化测试及执行结果；
- 可重复的手工复现步骤；
- 数据库或审计日志；
- 外部系统返回 ID；
- 截图、视频、扫描报告或恢复演练记录。

### 3.3 正反路径并重

除正常流程外，必须验证越权、过期授权、重复请求、旧版本写入、Worker 崩溃、网络超时、响应丢失、重定向、脏数据、部分失败和回滚场景。

### 3.4 自动化与人工审查互补

lint、类型检查、单元测试和扫描器已经覆盖的内容不重复做机械检查。人工 Review 聚焦跨模块规则、隐含假设、真实集成、异常恢复和用户体验一致性。

## 4. Review 阶段与工期

| 阶段 | 建议工时 | 核心工作 | 交付物 |
| --- | ---: | --- | --- |
| 1. 范围与基线冻结 | 0.5 天 | 固定 commit、发布范围、目标环境和外部依赖；执行基础检查 | 基线报告、环境差异表 |
| 2. 架构与业务不变量 | 1 天 | 审查 G0–G8、状态机、证据链、审批与自动化边界 | 架构图、不变量追踪矩阵 |
| 3. 安全与合规 | 1–1.5 天 | 身份、RBAC、SSRF、Secret、来源权利、Webhook、媒体访问、法律操作 | 威胁模型、安全发现清单 |
| 4. 数据与并发一致性 | 1–1.5 天 | 事务、幂等、ETag、租约、分页、重试、DLQ、删除和迁移 | 并发场景表、数据风险清单 |
| 5. API、UI 与可维护性 | 1–1.5 天 | 契约一致性、页面宽度、统一导航、响应式、可访问性及热点模块 | UI 一致性矩阵、API 差异、重构建议 |
| 6. 生产与故障演练 | 1 天 | 外部集成、备份恢复、回滚、限流、容量和告警 | 演练记录、生产缺口表 |
| 7. 汇总与复核 | 0.5 天 | 风险定级、修复确认和发布决策 | 最终报告、整改 Backlog |

单人完整执行预计 6–7 个工作日；两名 Reviewer 并行预计 3–4 个工作日。真实外部验收以及 28 天 SLO 观察作为独立验收周期管理。

## 5. 详细 Review 清单

### 5.1 架构与核心业务不变量

- 从 `lib/workflow.ts` 出发，逐条追踪 G0–G8 的决策、调用方、持久化数据和测试。
- 验证任何 API、Worker、脚本和调度路径都不能跳过状态或弱化门禁。
- 验证研究审批人和发布审批人必须为不同的有效成员。
- 验证来源申请人与权利审批人、legal hold 操作者之间的职责分离。
- 验证人工编辑、人工审批和内容事件能够把项目可靠切换为人工模式。
- 验证审批、QC 和发布绑定同一份不可变快照及正确的 SHA-256 哈希。
- 验证 synthetic evaluation 不会被描述为真实财经金标或 Social Evidence 验收结果。

### 5.2 身份、安全与合规

- 验证本地角色模拟只能用于 loopback，生产请求忽略客户端伪造角色头。
- 验证认证代理未配置时系统拒绝访问，而不是降级为匿名管理权限。
- 将每个写接口与 `SOURCE_ACTION_ROLES`、项目角色规则及 OpenAPI security 定义逐项比对。
- 检查来源 Worker、渲染 Worker、控制面和调度器的环境变量白名单与 Secret 可见范围。
- 检查所有外部 URL 的协议、重定向、DNS 解析、私网地址、IPv4/IPv6 特殊地址及大小限制。
- 验证 Webhook HMAC、重放窗口、媒体对象签名、过期时间和对象级授权范围。
- 验证来源权利授权与当前配置哈希绑定，并在最终提交事务内再次判断。
- 检查日志、错误响应、DTO、审计 metadata 和构建产物是否泄露 token、原始载荷或个人信息。
- 复核镜像非 root、只读边界、构建上下文、依赖漏洞、Secret 扫描和 SBOM 产物。

### 5.3 数据、事务与并发

- 识别所有跨表写入，确认事务边界覆盖状态、业务数据、审计事件和后续作业。
- 项目不使用数据库外键，因此需要 100% 检查删除、撤回、归档、legal hold、保留策略和来源失权路径。
- 验证 ETag/expectedVersion 在实际写入语句中参与条件判断，而不只是入口校验。
- 验证相同幂等键与相同请求可精确重放，不同请求不能复用相同键。
- 验证 Worker owner、lease epoch、到期时间和作业状态同时参与续约及完成判断。
- 验证响应丢失、租约过期、Worker 崩溃和重复领取不会倒写已完成状态。
- 验证分页采集的 page key、ordinal、checkpoint、final manifest 和累计数不可伪造或断页。
- 验证 raw payload 先持久化、再引用、最后按保留策略安全删除的顺序。
- 验证迁移不可变 checksum、重复执行幂等性、旧版本升级、回滚策略和恢复后校验。

### 5.4 API 与契约

- 对每个写路由检查请求 schema、响应 schema、权限、幂等、版本冲突和稳定错误码。
- 对每个读取路由检查字段 allowlist、分页稳定性、跨租户或跨来源读取边界。
- 比对 `contracts/openapi.yaml`、路由实现、客户端 DTO 和页面调用。
- 验证 breaking-change baseline 固定，不会随普通提交漂移。
- 检查弃用窗口、错误 envelope、枚举值和状态词汇的一致性。
- 明确 OpenAPI 未覆盖的内部协议，并说明其版本策略和兼容性责任人。

### 5.5 UI 页面宽度统一

当前页面同时使用 `max-w-5xl`、`max-w-6xl`、`max-w-7xl`、`max-w-[1480px]` 和 `max-w-[1500px]`，页头与正文也存在宽度不一致。Review 需要产出统一的页面容器规范，而不是逐页继续硬编码。

建议定义三种受控布局规格：

| 布局规格 | 建议使用场景 | 宽度原则 |
| --- | --- | --- |
| Standard | 待办、自检、自动化、普通配置页面 | 统一标准内容宽度，例如 `max-w-6xl` |
| Wide | 雷达、治理、来源管理、运营大盘 | 统一宽屏宽度，例如 `max-w-7xl` 或项目约定的固定 token |
| Workspace | 项目工作台等三栏生产界面 | 允许更宽，但必须使用唯一 workspace token |

具体检查项：

- 页头和正文必须使用同一个容器组件或同一组宽度 token。
- 左右 padding、顶部间距和 section gap 在相同断点下保持一致。
- 不允许业务组件继续新增任意 `max-w-*` 值；特殊宽度必须有明确场景和说明。
- 检查 320、375、768、1024、1280、1440 和 1920 像素视口。
- 页面在窄屏下不得出现非预期横向滚动；表格、图表和多栏布局需要有明确降级方式。
- 弹窗、抽屉和视频预览属于局部容器，不纳入页面主容器宽度，但仍需遵守组件级规格。
- 建议最终抽取 `PageShell`、`PageHeader`、`PageContainer` 或等价共享组件，并通过变体表达 Standard、Wide、Workspace。

页面验收矩阵至少覆盖：

- `/`
- `/sources`
- `/projects/[id]`
- `/automation`
- `/inbox`
- `/operations`
- `/governance`
- `/settings/diagnostics`

每个页面记录：布局规格、页头宽度、正文宽度、移动端表现、横向溢出、截图结果和差异结论。

### 5.6 全站导航统一

当前多个页面自行实现页头与“返回雷达”按钮，导航入口、层级提示和当前页面状态不完全统一。Review 应形成唯一的信息架构和全站导航模式。

导航建议分为：

- 一级导航：雷达、来源、自动化、待办、运营、治理。
- 系统入口：系统自检及其他设置能力。
- 上下文导航：项目工作台的生产阶段导航。
- 层级导航：项目详情、来源详情等深层页面使用面包屑或明确的父级返回入口。

具体检查项：

- 所有一级页面使用同一个导航组件和同一份导航配置。
- 当前页面必须具有稳定的 active 状态，并设置合适的 `aria-current`。
- 页面名称、图标、顺序和 URL 在桌面端与移动端保持一致。
- 不再由每个页面分别维护“返回雷达”“待办箱”等临时按钮组合。
- 项目工作台的阶段导航属于二级上下文导航，不应与全站一级导航混合。
- 导航需要支持键盘操作、可见焦点、合理 tab 顺序和屏幕阅读器标签。
- 移动端应有统一的折叠导航方案，并确保打开、关闭和焦点回收正确。
- 权限不足的入口需统一选择“隐藏”或“禁用并解释”，不能在不同页面采用不一致行为。
- 页面刷新、深链接和浏览器前进/后退后，active 状态和上下文不能丢失。
- 导航变更需补组件测试，并对八个主要页面进行截图或浏览器回归。

UI Review 的最终产出应包括：信息架构表、页面容器 token、共享导航组件建议、桌面与移动端基准截图，以及逐页差异清单。

### 5.7 可维护性与热点模块

优先审查以下模块：

- `components/source-manager.tsx`：约 3266 行。
- `lib/control-plane.ts`：约 2619 行。
- `db/schema.ts`：约 1840 行。
- `lib/orchestrator.ts`：约 1708 行。
- `render-worker/worker.ts`：约 1304 行。
- `app/api/v1/ingestion-runs/[id]/commit/route.ts`：约 817 行。

审查重点不是按行数机械拆分，而是：

- 是否混合领域决策、持久化、协议转换和 UI 状态；
- 是否存在重复状态词汇、权限规则或错误映射；
- 是否可以缩小事务和变更影响范围；
- 是否容易为失败路径增加测试；
- 是否存在高分支复杂度、超长函数和隐式共享状态；
- 拆分后是否仍能维持业务不变量的单一权威来源。

### 5.8 测试与质量门禁

- 执行 `make check` 作为日常基线，执行 `make verify` 作为完整本地发布门禁。
- 在 CI 中显式确认 lint、typecheck、OpenAPI、测试、评估、迁移、构建、渲染和恢复演练均有独立失败信号。
- 统计行、分支和函数覆盖率，但按关键不变量及失败场景判断覆盖质量。
- 为权限矩阵、状态转换和错误码采用表驱动测试。
- 为租约、幂等、分页和预算增加确定性并发或故障注入测试。
- 为页面宽度和导航建立统一的浏览器视口回归矩阵。
- 配置真实 R2 时，契约测试失败不得自动降级为跳过或成功。
- 区分 synthetic regression、真实历史数据集和生产观察数据，报告中不得混用。

### 5.9 外部集成与生产运维

- 认证代理：使用至少两个不同真实账号验证身份映射、权限和 G7 异人审批。
- R2：验证普通上传、分片上传、校验和、元数据、删除、保留和恢复。
- OpenAI TTS：验证生产 Secret、授权声音、限流、重试、费用和失败降级。
- YouTube：在测试频道验证续传、private fail-safe、返回 ID、更正和下架。
- OpenCLI/Browser Bridge：验证真实运行环境、账号权限、命令隔离和失败行为。
- 来源：使用已授权中文来源验证订阅、调度、checkpoint、质量门禁和 provenance。
- 备份恢复：在隔离环境验证数据库恢复、对象引用、审计连续性和 RTO/RPO。
- 监控：验证 Worker 心跳、积压、DLQ、SLO、预算、存储和发布失败告警。
- 回滚：明确应用版本、数据库迁移、Worker 协议和连接器版本的回滚顺序。

## 6. 风险分级

| 级别 | 定义 | 处理要求 |
| --- | --- | --- |
| P0 | 可导致越权、错误公开发布、门禁绕过或不可逆数据损坏 | 立即停止发布，优先修复并专项复核 |
| P1 | 高概率生产事故、错误采集、幂等失效或恢复失败 | 发布前必须修复 |
| P2 | 局部正确性、性能、可观测性、UI 一致性或高维护成本问题 | 纳入最近迭代并明确责任人 |
| P3 | 低风险可读性、结构优化或一般技术债 | 纳入 Backlog |

发现的优先级由影响、发生概率、可检测性和可恢复性共同决定，不能仅以修改成本降级。

## 7. 每项发现的记录模板

```md
## [P1] 发现标题

- 范围：模块、接口或页面
- 证据：文件与行号、日志、截图或测试名称
- 前置条件：触发该问题所需条件
- 复现步骤：可重复执行的最短路径
- 实际结果：当前行为
- 预期结果：应满足的不变量或产品规范
- 影响：安全、数据、业务、用户或运维影响
- 建议修复：推荐方向及必要约束
- 验证方式：自动测试、手工验证或外部验收
- 责任人：明确到角色或人员
- 目标版本：计划进入的版本或迭代
- 状态：Open / Fixing / Ready for re-review / Closed / Accepted risk
```

## 8. Review 交付物

1. 管理层摘要：总体风险、是否建议发布、主要阻断项。
2. 技术发现清单：按 P0–P3 排序，包含完整证据和修复建议。
3. 核心不变量追踪矩阵：不变量 → 实现 → 测试 → 运维证据。
4. API 契约差异表：OpenAPI、服务端、客户端和错误模型的差异。
5. UI 一致性矩阵：每个页面的宽度规格、导航模式、响应式和可访问性结果。
6. 外部验收缺口表：环境、凭据、真实上游、责任人和完成条件。
7. 整改 Backlog：优先级、负责人、工作量、目标版本和依赖关系。
8. Re-review 记录：修复前后证据及残余风险。

## 9. 发布决策标准

### 建议发布

- 无未关闭的 P0、P1。
- 所有关键业务不变量均有实现与测试证据。
- 数据迁移、备份恢复和回滚路径已在目标等价环境验证。
- 目标发布所需的外部集成已完成真实验证。
- 八个主要页面满足统一宽度、导航和响应式验收标准。
- 已知 P2、P3 均有责任人和目标版本。

### 有条件发布

- 无 P0；个别 P1 有经过业务、安全和技术责任人共同批准的临时缓解措施。
- 缓解措施可观测、可回滚，并设置明确的失效日期。
- 未验收功能保持关闭或 fail-closed，不对外宣称已接受。

### 不建议发布

- 存在任何未关闭的 P0。
- 身份代理、来源授权、发布保护或数据恢复无法证明有效。
- 关键迁移未应用或无法恢复。
- 自动化可能绕过人工审批、证据门禁或预算限制。
- 外部能力尚未验证但在生产配置中默认开启。

## 10. 建议执行顺序

1. 冻结 Review commit，并保存基础命令结果。
2. 建立核心不变量和写路由清单。
3. 并行开展安全合规审查与数据并发审查。
4. 完成 API 契约检查及 UI 宽度、导航一致性检查。
5. 在具备凭据和网络权限的隔离环境执行外部集成与恢复演练。
6. 汇总 P0–P3，召开一次发现校准会议。
7. 修复 P0/P1，并针对修复内容进行定向 Re-review。
8. 由技术、产品、安全/合规和运维责任人共同做最终发布决策。
